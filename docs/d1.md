# D1

The Worker binds one D1 database as `DB`. This page covers the databases and the config entries
that name them, how migrations reach each database, local development, tests, the database that
every Preview shares, and the Wrangler behavior that can turn a command against production.

## Databases and config entries

Production and the Previews each have a remote database. Local development and tests use local
databases that Wrangler creates, so they never touch a remote one.

| Database                        | Used by       | Config entries                                                                                                           |
| ------------------------------- | ------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `cloudflare-starter-db`         | Production    | The top-level `d1_databases` in `wrangler.jsonc`, binding `DB`                                                           |
| `cloudflare-starter-db-preview` | Every Preview | `previews.d1_databases` in `wrangler.jsonc`, binding `DB`, and `wrangler.preview-migrations.jsonc`, binding `PREVIEW_DB` |

- The top-level entry is the production binding. Its `migrations_dir` names the `migrations/`
  folder, and local development and tests use it too.
- The `previews` entry binds the Previews database as `DB`, so the code reads the same binding
  everywhere. Previews inherit nothing from production, so without it a Preview has no `DB`.
- `wrangler.preview-migrations.jsonc` declares only the Previews database, at its top level, so the
  Preview workflow can migrate it. [Name resolution](#name-resolution) explains why it exists.

Each `database_id` starts as a placeholder. Replace the placeholders with the IDs that
`pnpm exec wrangler d1 create <name>` prints, and keep the Previews database's ID the same in both
files that name it.

## Migrations

A migration is a numbered SQL file in `migrations/`. The folder ships empty, so no example table
ever reaches a production database. Create a migration with
`pnpm exec wrangler d1 migrations create DB <name>`, which adds the next numbered file.

Wrangler records each applied migration in the `d1_migrations` table of the database, and applies
only the files that aren't recorded there. Each database moves forward on its own:

- **Production:** after the build and before the deploy, `.github/workflows/deploy.yml` runs
  `pnpm exec wrangler d1 migrations apply DB --remote`. The schema is ready before the new code
  starts, and a failed migration stops the deploy.
- **Previews:** before each Preview deploy, `.github/workflows/preview.yml` runs
  `pnpm exec wrangler d1 migrations apply PREVIEW_DB --remote --config wrangler.preview-migrations.jsonc`.
- **Local:** `pnpm db:migrate` applies the migrations to the local database.
- **Tests:** a setup file applies them to a fresh database for each test file.

Migrations only add tables and columns. To rename or drop one, first ship code that stops using
it, then remove it in a later change. Additive migrations keep two things working:

- During a deploy, the old code runs against the new schema until the new version takes over.
- A pull request's migration reaches the shared Previews database before the pull request
  merges, so every other Preview runs against it.

## Local development

`pnpm dev` reads the local database in `.wrangler/state` and never applies migrations itself. Run
`pnpm db:migrate` after you add a migration or pull one from another branch. It runs
`wrangler d1 migrations apply DB --local`, which writes to the same local state.

To start the local database over, delete `.wrangler/state/v3/d1` and run `pnpm db:migrate` again.

## Tests

Tests never read the local database from `pnpm dev`. `vitest.config.ts` reads the migrations, and
`test/helpers/d1.ts` applies them before each test file, which starts with its own empty
database. [testing.md](testing.md#test-d1) has the details.

## The shared Previews database

Every Preview binds the same database, so:

- Rows that one Preview writes are visible to every other Preview.
- A migration from a pull request stays in the database after the pull request closes, whether it
  merged or not.
- Two pull requests that carry the same new migration can both try to apply it, and the second
  run fails because the first one applied it in the meantime. The Preview workflow tries up to
  three times, and the retry finds the migration recorded. Nothing serializes the runs, because a
  concurrency group across pull requests would let GitHub cancel a pending Preview.
- Two pull requests whose migrations conflict, such as two different tables with one name, fail
  on every attempt. The later pull request needs a different migration.

To undo what pull requests left behind, restore the Previews database to an earlier time with
D1 Time Travel:

```sh
pnpm exec wrangler d1 time-travel restore PREVIEW_DB --config wrangler.preview-migrations.jsonc \
  --timestamp <RFC 3339 timestamp>
```

The restore also rewinds `d1_migrations`, so the next push to each open pull request applies its
migrations again. To start from an empty database instead, create a new one, put its name and ID
in both `previews.d1_databases` and `wrangler.preview-migrations.jsonc`, and delete the old one in
the Cloudflare dashboard.

## Name resolution

Wrangler's D1 commands look up their database argument in the top-level `d1_databases` of the
config they read, by binding or by name, before they ask the Cloudflare API. They never read
`previews.d1_databases`. Inside this repository, `DB` therefore means the production database:

- `wrangler d1 migrations apply DB --remote` migrates production, even on a pull request branch.
- `wrangler d1 execute DB --remote` runs SQL against production.
- `wrangler d1 delete DB` deletes production.

After `pnpm build`, Wrangler reads the build's output config through `.wrangler/deploy/config.json`,
which carries the same `d1_databases`, so the lookup is the same.

Follow these rules:

- Don't apply migrations with `--remote` by hand. The workflows apply them.
- To act on the Previews database, name `PREVIEW_DB` and pass
  `--config wrangler.preview-migrations.jsonc`. `PREVIEW_DB` appears in no other config, so a
  command that forgets `--config` fails instead of reaching production.
- Don't run `wrangler d1 delete` or `wrangler d1 execute --remote` with a binding name inside the
  repository.
